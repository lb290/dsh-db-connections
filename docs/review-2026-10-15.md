## 0. 总体评价

分层是清楚的：`config.js`（归一化/校验）→ `registry.js`（执行）→ `live.js`（热替换）→ `tools.js`/`prompt.js`/`api.js`（对外），状态只有一个权威来源（profile 的 `cordis.patch.yml`）。有几个决定明显高于同类插件的平均水平，建议保持：

- **只读由服务端强制**（`START TRANSACTION READ ONLY`），而不是靠关键字黑名单——黑名单永远会漏。
- **名字进提示词、工具只收名字**，工具 schema 不变（避免了 schema 与连接列表不同步）。
- **`rowsAsArray` + 独立的 `columns`**，不给每一行重复列名；`dateStrings`/`decimalNumbers`/`bigNumberStrings` 不自己发明精度和时区。这两条直接省 token、省事故。
- **错误翻译成人话**（`describeFailure` 那张 code→文案表），对模型很友好。
- **`passwordEnv` 让口令不落盘**（虽然实现有两个坑，见 P0-2/P0-3）。
- 10 个测试，包括 CTE 写和 `INTO OUTFILE` 的绕过用例。

下面按优先级列问题。带 `文件:行` 的都能直接跳过去看。

## P0 先修（安全 / 静默出错）

### P0-1 设置页 GET 把明文密码发回浏览器

`api.js:114` 的 GET 直接返回 `list()`，而 `list` 是 `store.load(mountedRaw)`（`index.js:99`）——它读的是 `cordis.patch.yml` 的**原始条目**，包含 `password` 明文。`client.js:286` 又把它渲染进一个明文 input。

后果：本机任意进程 `curl 127.0.0.1:<port>/api/db-connections` 就能拿到所有库的口令。跨源浏览器读取被 CORS 挡住了（响应没有 `ACAO` 头），但 Origin 检查是 `Origin == Host`（`api.js:66-76`），DNS rebinding 下两边都是攻击者域名，一样通过。

建议（改动最小）：

1. GET 永不返回 `password`，只返回 `passwordSet: true|false`。
2. POST 里「字段缺失」= 保持不变，只有显式传 `""` 才清空。这样 UI 是只写输入框，不需要把密文发回来。

这正是 harness 自己的做法：`packages/settings/settings/src/redact.ts` 的 `role('secret')` + `SettingsForms.mutate(ns, ops, expectedRevision)`——按路径改字段、从不重述密文，还顺带带乐观锁（见 P3-2）。如果注入 `ctx.settings` 并声明 Schemastery `Config`（`password: z.string().role('secret')`），这些是白送的；但你们当初为了「任意路径可加载」刻意不依赖 harness 包（`config.js:5-8` 的注释），所以这条要先验证你们的安装方式能否 resolve `@deepseek-ai/schemastery`。验证不通过就按上面 1+2 自己实现。

### P0-2 一次保存会静默毁掉 `passwordEnv`（凭据丢失）

`client.js` 的 `toPayload()`（335-359）只发 `password`，从不发 `passwordEnv`；而 `toEditor()`（366-380）通过 `{...BLANK, ...raw}` 把 `passwordEnv` 留在了编辑器状态里，只是没渲染、也没回传。

后果：一个手写成 `passwordEnv: WAREHOUSE_PW` 的连接，只要在设置页点一次保存（**哪怕只是新增了另一个连接**），服务端 `resolvePassword`（`config.js:114-124`）就改成读 `password`，落盘成 `password: ''`——连接静默变成空密码。README 说 `passwordEnv` 是「手改选项」，但手改的东西会被 UI 覆盖掉。

修：`toPayload` 原样回传 `passwordEnv`；或者在卡片上给「密码来源：明文 / 环境变量」一个选择器（后者填变量名）。

### P0-3 一个坏的环境变量会连设置页一起打死

`config.js:119-122`：`passwordEnv` 指向的变量不存在就 throw；`apply()` 第 53 行是同步调用的，于是**整个插件加载失败** → `webServer` 路由不注册 → 设置页只能显示「无法读取配置」，而用户唯一的修复入口恰恰就是这个页面。只能去手改 YAML。

建议：单个连接解析失败降级为「该连接不可用 + 原因」，插件整体加载成功，页面顶部显示告警条；只有结构性错误（不是 mapping、名字重复、driver 不支持）才 throw。harness 的约定是「misconfiguration fails loud」，但指的是不静默跳过，不是把修复入口一起炸掉。

### P0-4 只读的「第二道防线」一换库就没了（这是多数据源的前置条件）

现在 `db_query` 的安全性**完全**来自 `registry.js:215` 的 `START TRANSACTION READ ONLY`。`classify()`（`sql.js:50`）只是「早点报错」：返回 `'unknown'` 时 `db_query` 是放行的（`registry.js:256` 只拒绝 `'write'`）。

MySQL 上这样没问题。但：

- **Doris**：显式事务只支持 `INSERT/UPDATE/DELETE`，官方文档明确「包含查询或 DDL 的多语句事务不支持」，也没有 MySQL 的 READ ONLY 事务模式。所以 `START TRANSACTION READ ONLY` 在 Doris 上要么语法报错，要么把 SELECT 包进事务被拒——**现在这条路在 Doris 上走不通**，需要在 Doris 上实测确认具体表现。
- **TDengine**：没有事务。

到那时 `classify` 就从「提示」变成**唯一防线**，而它现在把 `WITH ... DELETE`、`SET ...`、`USE`、`PREPARE/EXECUTE` 全部当 `'unknown'` 放行。

建议（多数据源动工前必须先做）：

1. driver 暴露 `readOnly: 'server' | 'classify'`。
2. `classify` 改成**白名单**：`db_query` 只放行明确的读关键字，`'unknown'` 一律拒绝，提示「要写请用 db_execute」或「改写成 SELECT」。MySQL 上两道防线都留着。
3. 对没有服务端只读能力的库，README/设置页明确建议配**只读账号**——这是唯一真正的强制手段。

顺带：`TABLE`、`VALUES` 只在 MySQL 8 是读；`SET/USE/PREPARE/EXECUTE/DEALLOCATE/ANALYZE/CHECK` 现在既不读也不写。关键字表要按 dialect 维护。

### P0-5 取连接失败的错误被当成「读」错误

`registry.js:177` 在 `#withConnection` 里对 `pool.getConnection()` 的失败硬编码传了 `'read'`，所以 `db_execute` 的连接失败会得到「db_query 的只读事务拒绝了它」这类牛头不对马嘴的文案。把 `mode` 传进 `#withConnection` 即可。

## P1 多数据源改造（PostgreSQL / Doris / TDengine）

### P1-1 先把「方言」和「驱动」拆开

现状是 `registry.js` 一个类里混了 mysql2、`information_schema` 查询、`SHOW CREATE TABLE`、`MAX_EXECUTION_TIME`、以及一张 MySQL 错误码表。建议：

```
src/drivers/<id>.js   唯一知道具体数据库的文件
src/registry.js       方言无关：行数裁剪、notices、只读策略、连接/池生命周期、AbortSignal
```

driver 接口（够用就好，别设计太大）：

| 成员 | 作用 |
| --- | --- |
| `defaultPort` | 端口默认值，替掉 `config.js:19` 的硬编码 |
| `open(connection)` / `dispose()` | 池的创建与释放 |
| `withConnection(connection, signal, fn)` | 借还连接 + abort 时销毁连接 |
| `readOnly` | `'server'` \| `'classify'`（决定 P0-4 的策略） |
| `classify(sql)` / `quoteIdent()` | 方言关键字白名单、标识符引用 |
| `guard(conn, connection)` | 只读 + 超时的会话级设置 |
| `read(conn, sql, limits)` | → `{columns, rows}` |
| `execute(conn, sql)` | → `{affectedRows, insertId, info, warnings}` |
| `schema(conn, target)` | 三级内省（库/schema → 表 → 列+索引+DDL） |
| `describeError(error)` | code → 人话 |
| `ping(conn)` | → `{version}` |

驱动包用 **dynamic `import()` 懒加载** + `optionalDependencies`，缺了报「请先 `npm i pg`」。别让只连 MySQL 的人被迫装 `pg`。

### P1-2 能力矩阵（这些差异必须落到代码里，不能假设「MySQL 协议兼容 = 通用」）

| | MySQL | Doris | PostgreSQL | TDengine |
| --- | --- | --- | --- | --- |
| 连接方式 | `mysql2` | `mysql2`（FE 查询端口，默认 **9030**） | `pg`（默认 5432） | HTTP REST（taosAdapter，默认 **6041**） |
| 只读强制 | 服务端只读事务 | 只能靠**分类 + 只读账号** | `default_transaction_read_only` | 只能靠**分类 + 只读账号** |
| 超时 | `MAX_EXECUTION_TIME`（ms） | `SET query_timeout=N`（**秒**） | `SET statement_timeout`（ms） | 无，仅客户端 abort |
| 事务 | 完整 | 仅 INSERT/UPDATE/DELETE | 完整 | 无 |
| 内省 | `information_schema` + `SHOW CREATE TABLE` | `information_schema` + `SHOW CREATE TABLE`/`SHOW INDEX` | `information_schema` + `pg_catalog` | `information_schema.ins_*` |
| 默认库语义 | `USE db` | `USE db` | 连接级绑定，只有 `schema.table` | 只能走 URL 路径 |
| 版本串 | `SELECT VERSION()` | 伪造的 MySQL 版本串 | `SHOW server_version` | `select server_version()` |

### P1-3 PostgreSQL 要点

- 只读：`SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`（或 `default_transaction_read_only=on`），写入报 SQLSTATE `25006`；超时用 `SET statement_timeout`（毫秒）。
- **`database` 语义不同**：PG 一个连接只能进一个库，限定名是 `schema.table`。现在 `db_schema` 的第一级是 `SHOW DATABASES`（`registry.js:392`），PG 上应改成列 schema（`information_schema.schemata` / `pg_namespace`）。建议把工具参数从 `database` 扩成 `schema`（`database` 保留为别名），prompt 里按 dialect 说明。
- 没有 `SHOW CREATE TABLE`：用 `pg_indexes` / `pg_get_indexdef` / `format_type(a.atttypid, a.atttypmod)` / `col_description` / `pg_class.reltuples`（估算行数，语义上和 MySQL 的 `TABLE_ROWS` 对齐）。
- **类型解析要显式设**：给 `pg.types.setTypeParser` 装上 `date/timestamp/timestamptz` 的原样字符串解析，才和你们 MySQL 侧 `dateStrings: true` 的决定一致（`registry.js:144`）。否则 `pg` 返回 JS `Date`，按本地时区往返，值会漂。

### P1-4 Doris 要点

- MySQL 协议，`mysql2` 能连，但：① 没有 `MAX_EXECUTION_TIME`，用 `SET query_timeout=N`（秒）；② 没有只读事务（P0-4），也大概率不接受 `SET SESSION TRANSACTION READ ONLY`；③ `information_schema.STATISTICS` 不一定存在，索引用 `SHOW INDEX FROM`；④ `information_schema.TABLES.ENGINE` 是 `OLAP`，`TABLE_ROWS` 是否可信要实测。
- `SELECT VERSION()` 返回的是伪造串（形如 `5.7.99 Doris version ...`），`client.js:274` 的 `MySQL {v}` 标签要按 driver 换文案。

### P1-5 TDengine 要点（走 REST，零原生依赖，和你们「无构建步骤」的风格一致）

- 端点 `POST /rest/sql/<db>`（默认 6041）；`Authorization: Basic base64(user:pass)`，也可以先 `GET /rest/login/<u>/<p>` 拿 token，再用 `Authorization: Taosd <token>`（避免每个请求都带上口令）。
- **REST 无状态，`USE db` 不生效**——默认库只能通过 URL 路径给。这正好对应配置里的 `database`，但驱动必须把它拼进 URL，而不是发 `USE`。
- 返回体 `{code, column_meta:[[name,type,len]], data, rows}`；出错是 `{code≠0, desc}`，而默认 `httpCodeServerError=false` 时**HTTP 状态码仍是 200**。所以 driver 必须自己判 `code !== 0` 并抛错，否则失败会被当成成功。
- 好处：`column_meta` 直接给列名 + 类型，比 MySQL 那边再查一次 `information_schema` 少一轮。
- 三级内省映射很自然：库 → `information_schema.ins_databases`；表 → `ins_tables`；列/tag → `ins_columns`（超级表信息在 `ins_stables`）。
- **时序语义要进 prompt 和 db_schema**：STABLE/子表/tag、`ts` 必须是第一列、`INTERVAL/SLIDING/FILL/PARTITION BY/LAST_ROW/WINDOW`。TDengine 单表动辄上亿行，默认 `maxRows` 建议降到 20–50，并在检测到查询没有时间范围时给 notice（有必要时直接拒）。
- 备选：`@tdengine/websocket`（6041 的 `/ws`）支持二进制、并发更好，但多一个依赖。建议先 REST。

### P1-6 顺手要改的小地方

- `config.js:13` `SUPPORTED_DRIVERS`、`config.js:19` `DEFAULT_PORTS` 加 `postgres: 5432`、`doris: 9030`、`tdengine: 6041`。
- `client.js:208` 和 `client.js:345` 把端口写死成 3306，要按 driver 取默认值；卡片上要加 driver 选择器。
- `tools.js:21-24` 的 connection 参数描述、`tools.js:72` 的「in MySQL syntax」、`prompt.js` 的文案，都要按该连接的 dialect 表述。
- `values.js` 基本够用（Buffer/Date/bigint/数组/JSON 都覆盖），TDengine 的时间戳是 ISO 字符串，PG 见 P1-3。

## P2 产出质量与 token 成本

1. **结果体积没有总量上限**：`maxRows: 200` × `maxCellChars: 500` 最坏约 100 KB，一次就进 ~25k tokens。建议加 `maxResultChars`（例如 32k）在渲染前截断并给 notice，并给工具加 `format: table|json|csv`——宽表用 TSV/JSON 比对齐表省得多，`renderTable` 的 `padEnd`（`tool.js:186`）对 200 行也是纯浪费。另外 CJK 列宽要用显示宽度算，`String.length` 会错位。
2. **提示词里带 `host:port`**（`prompt.js:18`）：模型要理解「用 128」只需要名字、用途、读写权限、引擎；内网拓扑每轮都在烧 token。连接一多这条会很明显。建议 prompt 只留名字+备注+权限+引擎，明细交给一个 `db_connections` 工具按需展开。
3. **缺工具**：① `db_find`——跨连接/跨库按表名搜索（四种引擎、几十个库的情况下，这是模型最大的摩擦点）；② schema 缓存（TTL + `refresh`），现在每次 `db_schema` 都要实打实查一遍 `information_schema`；③ 外键（PG/MySQL 都能给）。
4. **完全没有日志**：`ctx.logger` 一次都没用。既然允许写，建议把 `db_execute` 落 JSONL 审计（时间/连接/语句摘要/影响行数/耗时/成败/发起方），团队用的时候这个比什么都值。可参考同类插件 `JohnXu22786/db-connector`（它也支持 SQLite/PG/MySQL，带审计、只读守卫、凭据走 env/credentials、`/db` 命令）：<https://github.com/JohnXu22786/db-connector>
5. **`timeoutMs: 120_000` 是常量**（`tools.js:82`、`tools.js:137`），和 per-connection 的 `queryTimeoutMs` 可能互相矛盾（配了 300s 也会在 120s 被 abort）。要么按连接推导，要么在 prompt 里说清楚。
6. **React `key={index}`**（`client.js:513`）：删掉中间一张卡片后，`Card` 内部的 `advanced`/`probe` state 会跟着位置串到别的连接上——测试按钮的结果会张冠李戴。用稳定 id 当 key。
7. harness 有 `ctx.commands`（`packages/interaction/commands`），可以加个 `/db` 人类命令，随手查一下不必每次都走模型一轮。

## P3 工程化

1. **`package.json` 没有 `scripts.test`**：10 个 `test-*.mjs` 只能手工一个个跑。加 `"test": "node --test"`（或一个跑全部的脚本），迁到 `node:test` 更好；再加个最小 CI（Node 22/24 矩阵）。没有 lint/format 配置。
2. **`files` 少了 `CHANGELOG.md`**。
3. **`store.js:148-150` 的 tmp+rename**：① 临时文件里是含明文口令的完整配置，建议 `writeFileSync(..., { mode: 0o600 })`，并检查/提示 patch 文件本身权限；② **没有并发保护**——CLI（`dsh plugin add`）、别的插件、设置页同时改同一个 `cordis.patch.yml` 会互相覆盖（最后写者赢）。至少做到「写前重读 + 确认没被改过」，或者加锁。harness 原生 `ctx.settings.mutate(ns, ops, expectedRevision)` 就是用 revision 解决这个的。
4. **`ssl` 只能是 true/false**：缺 CA、客户端证书、`rejectUnauthorized`（内网 mTLS 很常见）。建议 `ssl: false | true | { ca, cert, key, rejectUnauthorized }`。
5. 生产库常在内网/跳板机后面，可以预留 `ssh` 隧道选项，至少在 README 写清楚怎么配现有隧道。
6. `tools.js:94-96` 那个「一个节点只能一个标量类型」的注释，我在 harness 侧没找到对应硬约束；如果 `type: ['string','null']` 是允许的，写清楚更好读。纯可读性问题。
7. 文案双份：`client.js:34-135` 的 `DICT` 和 `locale/*.json`（只有 meta）是两处，多方言改造时容易漂。

**关于验证覆盖的诚实说明**：本机没有任何数据库，所以 2 个真库套件（`test-integration`、`test-write`）没有执行过。为了不把「编排层」也留成盲区，`ConnectionRegistry` 的驱动工厂做成了可注入的接缝，`test-registry.mjs` 用替身引擎覆盖了 41 项断言：行数截断提示、单元格转换（Buffer/Date/bigint/超长/CJK）、三种输出格式与 `maxResultChars` 预算、只读策略的四条分支、写路径与审计记录（含失败记录）、schema 三级渲染、参数校验、连接释放。引擎各自的**协议细节**（真实 SQL、握手、错误码、目录查询的列名）仍然只由 `test-drivers` 的纯函数层覆盖，需要你在真库上跑一次确认。

未做，保留为后续（都已写进 README 的 Known Limitations 或本节）：

- **`ctx.settings` 原生化**：schema 派生表单 + `role('secret')` 脱敏 + revision 乐观锁是 harness 自带的；本版用等价语义手写实现，如果你们的安装方式能 resolve `@deepseek-ai/schemastery`，值得迁过去，能删掉不少代码。
- **`ctx.credentials` 的 `passwordRef`**：比自建 `passwordEnv` 更原生，且是按次解析（改了环境变量下一次调用就生效）。
- **`db_find`（跨连接按表名搜索）与 schema 缓存（TTL）**：四个引擎几十个库时，这是模型最大的摩擦点。
- **SSH 隧道 / 堡垒机选项**：生产库常在内网，先按现有隧道用。
- **会话级只读以省掉每条语句 2 次 RTT**：现在的写法（每条语句开一个只读事务）更安全，还顺手挡住了 CTE 绕过；只有跨 WAN/高延迟时才值得换成分离的读写池。
